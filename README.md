# Cookie Creations: Sales Database and Dashboard

Sales data for a fictional cookie business. The data started out in Microsoft Access. It now lives in PostgreSQL, and a Power BI report is built on top of it.

```
archive/*.accdb ──► scripts/migrate_access_to_postgres.py ──► PostgreSQL: cookie_creations
                                                                 ├─ public.customers / products / orders
                                                                 └─ analysis.* views (the five business questions)
                                                                        │
                                                                        ▼
                                                     CookieDB Visualisation.pbip (Power BI)
```

## What the dashboard answers

The Power BI report has five pages, and each one answers one of the original analysis questions. The SQL behind each answer is a view in `sql/02_analysis_views.sql`.

| Page | Question | View |
|---|---|---|
| Overview | How is the business doing? Revenue, orders, monthly trend, progress to the £70k target | (rollups over `orders`) |
| Products | What are the total sales for each product? | `analysis.total_sales_by_product` |
| Customers | What is the total revenue generated by each customer? Which customers have placed the most orders? | `analysis.revenue_by_customer`, `analysis.customers_by_order_count` |
| Fulfilment | Which orders have not been filled? | `analysis.unfilled_orders` |
| Latest month | What are the details of orders placed in the last month? | `analysis.orders_last_month` |

Headline figures: £47,536.26 revenue from 100 orders by 46 of 50 customers. Sugar Cookie is the top seller at £12,382.50. 48 orders are unfilled.

## Getting started

Requirements:
- Windows, with the 64-bit Microsoft Access ODBC driver (only needed to re-run the migration)
- PostgreSQL 16 or later
- [uv](https://docs.astral.sh/uv/)
- Power BI Desktop

Postgres credentials come from the usual libpq settings: `PGHOST`, `PGPORT`, `PGUSER`, `PGPASSWORD`, or `pgpass.conf`. The defaults are `localhost` and `postgres`.

1. **Build the database.** This creates `cookie_creations` if needed, then drops and reloads everything:
   ```
   uv run scripts/migrate_access_to_postgres.py
   ```
2. **Open the Power BI report.**
   - Open `CookieDB Visualisation.pbip` and click **Refresh**.
   - Sign in with a Postgres database login.
   - If your local server has SSL turned off, accept the unencrypted-connection prompt.

If `uv` reports a certificate error (`invalid peer certificate`), add `--native-tls`, e.g. `uv run --native-tls scripts/...`.

## Data model

- **Tables:**
  - `customers` (50 rows)
  - `products` (5 rows)
  - `orders` (100 rows, 2 Jan to 16 Jul 2024)
- **Relationships:** `orders.customer_id → customers` and `orders.product_id → products`.
- **Changes from the Access design:**
  - The `Order` table is renamed to `orders`.
  - All names are snake_case.
  - The duplicate product key (`ID` and `CookiesID`) is merged into one `product_id`.
  - Types are proper integers, `numeric(10,2)`, `date` and `boolean`.
  - The relationships are enforced foreign keys (Access had them defined but not enforced).
- **Power BI model:**
  - Adds a `Date` table, the `Order Status` and `Customer Name` columns, and the measures used by the report (`Total Revenue`, `Fill Rate`, `Latest Month Revenue`, …).

## Data caveats

- Stored `revenue` does not equal `cookies_ordered × price_per_cookie`, and `price_per_cookie` does not match the product list price. All figures use the stored revenue, as the original Access queries and dashboard did.
- The data ends on 16 July 2024. "Latest month" therefore means July 2024, a partial month. It is compared with the same days of June.

## Archive

The original Access/Excel version of the project, kept for reference. The migration script still reads its source data from here.

| File | What it was |
|---|---|
| `archive/Database_for_Cookie_Creations_Database_Project.accdb` | The original Access database: tables plus five saved queries |
| `archive/tables/*.xlsx` | Excel exports of the Customers, Orders and Products tables |
| `archive/queries/*.xlsx` | Excel exports of the five Access queries, renamed after the SQL views that replace them |

The Access queries were plain joins with no grouping or filtering. That is why every export has 100 rows, one per order, and none of them actually answers its question. The SQL views replace them.
